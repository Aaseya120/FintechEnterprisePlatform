4. Fund Transfer — Saga Orchestrator Sequence

Distributed transaction: debit → credit → compensate if fails → Kafka event → notification

sequenceDiagram
    autonumber
    actor Customer
    participant GW as API Gateway
    participant PAY as Payment Service
    participant FRAUD as Fraud Detection
    participant ACC as Account Service
    participant DB as Database
    participant KAFKA as Kafka
    participant NOTIF as Notification

    Customer->>GW: POST /transfers + JWT + Idempotency-Key
    GW->>PAY: Route request

    rect rgb(230, 240, 255)
    Note over PAY,FRAUD: Step 1: Fraud Check
    PAY->>FRAUD: Check velocity and geo rules
    FRAUD-->>PAY: APPROVE (low risk)
    end

    rect rgb(230, 255, 230)
    Note over PAY,ACC: Step 2: Debit Source
    PAY->>DB: Save Transfer (INITIATED)
    PAY->>ACC: Debit source account
    ACC-->>PAY: Debit success
    PAY->>DB: Update (DEBITED)
    end

    rect rgb(255, 245, 230)
    Note over PAY,ACC: Step 3: Credit Target
    PAY->>ACC: Credit target account
    alt Credit Succeeds
        ACC-->>PAY: Credit success
        PAY->>DB: Update (COMPLETED)
        PAY->>DB: Write outbox event
    else Credit Fails
        Note over PAY,ACC: COMPENSATION: Auto-refund
        PAY->>ACC: Refund source account
        PAY->>DB: Transfer → COMPENSATED
    end
    end

    rect rgb(245, 235, 255)
    Note over PAY,NOTIF: Step 4: Async Event
    PAY->>KAFKA: Publish event via outbox
    KAFKA->>NOTIF: Consume → SMS + Push
    end

    PAY-->>Customer: Transfer result

stateDiagram-v2
    [*] --> INITIATED

6. JWT Authentication Flow

Login → token issue → authenticated request → token refresh lifecycle

sequenceDiagram
    autonumber
    actor User as Mobile / Web
    participant Auth as Auth Controller
    participant Filter as JWT Filter
    participant API as Banking APIs
    participant DB as Customer DB

    Note over User, DB: Phase 1 — Login
    User->>Auth: POST /auth/login (username, password)
    Auth->>DB: Verify BCrypt password
    Auth-->>User: Access Token (15 min) + Refresh Token (7 day)

    Note over User, API: Phase 2 — API Call
    User->>Filter: GET /accounts (Bearer token)
    Filter->>Filter: Verify HMAC-SHA256 + expiry + roles
    Filter->>API: SecurityContext set → execute
    API-->>User: 200 OK

    Note over User, Auth: Phase 3 — Token Refresh
    User->>Filter: GET /accounts (expired)
    Filter-->>User: 401 Unauthorized
    User->>Auth: POST /auth/refresh
    Auth->>DB: Rotate refresh token
    Auth-->>User: New tokens issued

9. Fraud Detection — Risk Scoring Engine

How transactions are scored and classified into risk tiers

flowchart TD
    TXN["Incoming Transaction"] --> VEL{"Velocity Check\n(Redis ZADD/ZCOUNT)"}
    VEL -->|"> 5 txns/60s"| HIGH["+40 Points"]
    VEL -->|Normal| AMT{"Amount Check"}

    AMT -->|"> $10K"| MED["+30 Points"]
    AMT -->|Normal| GEO{"Geo Check\n(Country mismatch)"}

    GEO -->|Mismatch| GEO_PTS["+25 Points"]
    GEO -->|Match| ZERO["+0 Points"]

    HIGH --> TOTAL["Total Risk Score"]
    MED --> TOTAL
    GEO_PTS --> TOTAL
    ZERO --> TOTAL

    TOTAL --> T{"Risk Tier"}
    T -->|0-24| APPROVE["✅ AUTO APPROVE"]
    T -->|25-49| MONITOR["👁️ POST-SETTLEMENT MONITOR"]
    T -->|50-79| STEP["🔐 STEP-UP AUTH"]
    T -->|80-100| BLOCK["🚫 IMMEDIATE HOLD"]

11. Reconciliation Engine

End-of-day matching of internal ledger vs external clearing records

flowchart TD
    TRIGGER["Trigger Recon Run"] --> EXT["Fetch External\nClearing Records"]
    EXT --> INT["Load Internal\nLedger Records"]
    INT --> STRAT{"Matching Strategy"}

    STRAT -->|Exact| EM["Match by\nRef ID + Amount"]
    STRAT -->|Tolerance| TW["Match within\n±threshold"]

    EM --> RES["Results"]
    TW --> RES

    RES --> MATCHED["✅ Matched\n(Count + Rate %)"]
    RES --> BREAKS["❌ Breaks\n(Mismatches / Orphans)"]

    BREAKS --> PERSIST["Persist with\nAudit Trail"]
    PERSIST --> RESOLVE["Manual Resolution\nby Auditor"]
