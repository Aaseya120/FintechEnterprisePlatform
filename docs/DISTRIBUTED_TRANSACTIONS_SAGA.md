# Distributed Transactions & Resilience Guide

## 1. The Dual-Write Problem in Microservices

In traditional monolithic enterprise applications, ACID transactions across multiple database tables are handled by local database transactions (`@Transactional`). In a distributed microservice architecture, an operation like **"Create Order and Process Payment"** spans separate databases and network boundaries:
1. `order-service` writes to the Order Database.
2. `order-service` sends a message to ActiveMQ or calls `payment-service`.

If the database commit succeeds but the network call fails (or vice versa), the system enters an inconsistent state. **Two-Phase Commit (XA / 2PC)** is not viable in modern cloud environments due to synchronous blocking, coordinator lock escalation, and poor availability under network partitions (CAP theorem).

---

## 2. Platform Solution: Transactional Outbox Pattern

To achieve **guaranteed eventual consistency** without distributed locks, this platform implements the **Transactional Outbox Pattern**:

### Database Schema (`FIN_OUTBOX_EVENTS`):
```sql
CREATE TABLE FIN_OUTBOX_EVENTS (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    aggregate_type VARCHAR2(64) NOT NULL,
    aggregate_id VARCHAR2(64) NOT NULL,
    event_type VARCHAR2(64) NOT NULL,
    payload CLOB NOT NULL,
    processed NUMBER(1) DEFAULT 0 NOT NULL,
    retry_count NUMBER(3) DEFAULT 0 NOT NULL,
    trace_id VARCHAR2(64),
    created_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_outbox_status ON FIN_OUTBOX_EVENTS(processed);
```

### Execution Flow:
1. Inside a single local ACID transaction in `OrderService`:
   ```java
   @Transactional
   public OrderResponse createOrder(CreateOrderRequest request) {
       // 1. Insert into FIN_ORDERS
       Order order = orderRepository.save(newOrder);

       // 2. Insert into FIN_OUTBOX_EVENTS in the EXACT SAME local transaction
       OutboxEvent outboxEvent = new OutboxEvent("ORDER", order.getOrderReference(), "ORDER_CREATED", payload, traceId);
       outboxEventRepository.save(outboxEvent);

       // 3. Fast-path synchronous gRPC invocation to PaymentService
   }
   ```
2. A resilient background poller (`OutboxPublisherJob`) monitors unprocessed records:
   ```java
   @Scheduled(fixedDelayString = "5000")
   public void publishOutboxEvents() {
       List<OutboxEvent> pending = outboxEventRepository.findPendingEvents();
       for (OutboxEvent event : pending) {
           jmsTemplate.convertAndSend(JmsConfig.ORDER_EVENTS_QUEUE, event.getPayload());
           event.setProcessed(true);
           outboxEventRepository.save(event);
       }
   }
   ```

## 3. Idempotency Guarantees with Redis

Because the Outbox poller guarantees **At-Least-Once Delivery**, network hiccups can cause duplicate messages. Consumers must be **strictly idempotent**:

1. Client sends a unique `IdempotencyKey` (UUID) with each request.
2. `OrderService` checks Redis:
   ```java
   String redisIdemKey = "idem:order:" + idempotencyKey;
   Boolean isNew = redisTemplate.opsForValue().setIfAbsent(redisIdemKey, "PROCESSING", Duration.ofMinutes(10));
   if (Boolean.FALSE.equals(isNew)) {
       // Return existing order without re-executing payment
       return orderRepository.findByIdempotencyKey(idempotencyKey)...
   }
   ```
3. `PaymentGrpcServiceImpl` checks payment deduplication before charging accounts.

## 4. Saga Compensation Flow

When a business rule fails downstream (e.g., Anti-Money Laundering threshold exceeded or customer credit limit breached):
1. `payment-service` publishes a `PaymentEvent(status=FAILED)` to `fintech.saga.compensation.queue`.
2. `order-service`'s `OrderCompensationConsumer` receives the event.
3. `order-service` transitions the Order status from `PAYMENT_PENDING` to `CANCELLED`.
4. Redis cache is updated (`@CachePut`), maintaining exact data alignment.
